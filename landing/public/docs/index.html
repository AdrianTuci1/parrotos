Documentation

Statsparrot is an analytics app for your warehouse and your files. You describe metrics as YAML in a folder you own, and you get dashboards, an OLAP engine, and an agent that explains what moved.

There are two ways to run it, and they share the same project files:

Locally One binary: statsparrot start serves the app on localhost. Hosted One container: users sign in, each project gets a runtime.

The project is the unit of work. It is a directory of YAML and SQL that you keep in git, review in a pull request, and roll back like any other code.

Install #

Prebuilt binaries exist for macOS (arm64) and Linux (amd64). The install script downloads the right one and puts statsparrot on your path. 

curl -fsSL https://get.statsparrot.com | sh
statsparrot version

The same binary runs in a container. It needs a C toolchain at build time because DuckDB is a C library linked into it, but the published image is self-contained: 

docker run --rm -p 9009:9009 -v "$PWD:/project" \
  ghcr.io/staticlabsro/parrot:latest start /project

Building from a checkout needs Go 1.26, Node 20 and a C toolchain:

git clone https://github.com/staticlabsro/parrotos
cd parrotos
make local-bin   # writes ./statsparrot

Quickstart #

init writes a starter project, including the agent instructions the local app reads. start builds it and opens the app on port 9009. 

statsparrot init my-project
statsparrot start my-project

A minimal project is three files:

my-project/
├── statsparrot.yaml     # project settings
├── orders.yaml          # a model: SQL over a connector
└── orders_metrics.yaml  # a metrics view: dimensions and measures

statsparrot validate my-project parses the project and reports errors without starting anything — useful in CI.

Project files #

Every file is a YAML document with a type, except statsparrot.yaml, which configures the project itself. The file name is the resource name: orders.yaml defines orders.

statsparrot.yaml # 

display_name: Orders
olap_connector: duckdb

# Project variables. Values written here are visible in the project settings;
# anything secret belongs in the environment, not in this file.
env:
  AWS_REGION: eu-central-1

# Directories the parser must not read as resources. SQL DDL that you run by
# hand lives here.
ignore_paths:
  - /athena

olap_connector picks the engine that answers queries. DuckDB is the default and needs no configuration; the warehouse connectors are below.

Models #

A model is SQL over a connector, materialized as a view. Metrics views read models, so a number is defined in one place. 

type: model
connector: duckdb
sql: |
  select TIMESTAMP '2026-01-01 00:00:00' as time, 'web' as channel,
         100 as revenue, 12 as orders
  union all
  select TIMESTAMP '2026-01-01 00:00:00', 'email', 60, 6

Metrics views #

A metrics view names a model, its time column, the dimensions you can slice by and the measures the dashboards and the agent can ask for. 

type: metrics_view
model: orders
timeseries: time
dimensions:
  - column: channel
measures:
  - name: total_revenue
    expression: sum(revenue)
  - name: order_count
    expression: count(*)

On a warehouse connector, add connector, database and table to read a table in place instead of a model: 

type: metrics_view
connector: athena
database: AwsDataCatalog
database_schema: analytics
table: behavioral_events
timeseries: event_ts
smallest_time_grain: hour

Canvases #

A canvas is a dashboard: a list of rows, and in each row a list of items that point at a metrics view. 

type: canvas
display_name: Overview

defaults:
  time_range: P4W

rows:
  - items:
      - kpi_grid:
          metrics_view: orders_metrics
          measures:
            - total_revenue
            - order_count

Connectors #

The connector is chosen per project (olap_connector) and, for warehouse-backed metrics views, per file. Each connector reads its credentials from the environment, so the same project runs locally and hosted.

Engine Notes
DuckDB The default. Reads local files and object storage; no credentials needed.
Postgres, MySQL, SQLite Point at a database and query it directly.
ClickHouse, Druid, Pinot, StarRocks Columnar engines for larger volumes.
BigQuery, Athena, Snowflake, Redshift, Databricks Warehouses. Credentials and, where relevant, a role to assume.
S3, GCS, Azure Blob, local files, HTTPS Object stores and flat files as sources.

A connector that needs credentials is a file next to the project. The values come from the environment, never from the file: 

type: connector
driver: athena

region: "{{ .env.AWS_REGION }}"
workgroup: "{{ .env.ATHENA_WORKGROUP }}"
output_location: "{{ .env.ATHENA_OUTPUT_LOCATION }}"

aws_access_key_id: "{{ .env.AWS_ACCESS_KEY_ID }}"
aws_secret_access_key: "{{ .env.AWS_SECRET_ACCESS_KEY }}"
role_arn: "{{ .env.ATHENA_ROLE_ARN }}"
role_session_name: statsparrot-dashboards

Those variables are project variables. Locally they come from a .env in the project directory; hosted, from the project's settings, which the CLI writes with statsparrot env set.

Hosted deployment #

One container runs statsparrot serve: the admin API, the web app, and a runtime that serves every project under /runtime, on a single origin. 

cd deploy/hosted
cp .env.example .env
# fill in the values below
docker compose up -d --build

These are required. The three secrets are checked at boot.

Variable Value
STATSPARROT_SERVE_PUBLIC_URL, STATSPARROT_DOMAIN The origin users open and its host. Register ${STATSPARROT_SERVE_PUBLIC_URL}/auth/login/callback as a redirect URI in the OIDC provider.
STATSPARROT_ADMIN_DATABASE_URL An empty Postgres 14+; the admin runs its migrations on boot.
STATSPARROT_ADMIN_SESSION_KEY_PAIRS, STATSPARROT_RUNTIME_SESSION_KEY_PAIRS openssl rand -hex 32
STATSPARROT_ADMIN_SIGNING_JWKS, STATSPARROT_ADMIN_SIGNING_KEY_ID statsparrot admin generate-signing-key prints both lines.
STATSPARROT_ADMIN_AUTH_DOMAIN, STATSPARROT_ADMIN_AUTH_CLIENT_ID, STATSPARROT_ADMIN_AUTH_CLIENT_SECRET Your OIDC tenant.
STATSPARROT_ADMIN_ASSETS_DRIVER, STATSPARROT_ADMIN_ASSETS_BUCKET gcs or s3, plus that bucket's credentials, for branding images and project archives.

STATSPARROT_SERVE_ROLE splits the deployment when one process should serve only part of it: all (the default), admin or runtime. The admin keeps its state in Postgres; the runtime keeps per-project data in STATSPARROT_SERVE_RUNTIME_DATA_DIR, which must be on persistent storage.

The first user to sign in has no organization. Create one, then create a project and connect it to a git repository; pushes to the watched branch redeploy it.

Running behind an access proxy. The CLI talks to the admin over gRPC-web at the same origin. A proxy that answers unauthenticated requests with an HTML login page (Cloudflare Access, an SSO gateway) breaks the CLI's JSON parsing, so give the CLI a service token for that origin or run it inside the network and pass --api-url.

CLI reference #

statsparrot <command> --help is authoritative for flags. These are the commands you will use day to day.

Local

statsparrot init <path> Create a project, including agent instructions.
statsparrot start [<path>] Build the project and serve the app on port 9009.
statsparrot validate <path> Parse the project and report errors without starting it.
statsparrot serve Run the hosted admin and runtime together.

Account

statsparrot login Device authorization: prints a code and a URL, then stores the token in ~/.statsparrot.
statsparrot whoami, logout, token issue Inspect the session, end it, or mint a token for automation.

Projects

statsparrot project connect-github Deploy a project from a git repository and redeploy on push.
statsparrot project deploy Upload the local files to a managed repository.
statsparrot project status, logs, refresh Deployment status, runtime logs, and a manual re-reconcile.
statsparrot project edit, rename, hibernate, delete Change settings, name, or lifecycle.
statsparrot env set <key> <value>, env show Project variables, used by connectors at query time.

Every cloud command takes --org and --api-url. The second one is how you point the CLI at a self-hosted admin instead of the public one.

Troubleshooting #

“yaml: control characters are not allowed”

The copy of the project the runtime is reading contains macOS metadata files (._statsparrot.yaml and friends), which are binary, not YAML. They are created when a folder is zipped, copied to a non-Apple filesystem, or uploaded from a Mac with extended attributes. Ignore them in git: 

printf '._*\n.DS_Store\n' >> .gitignore

“failed to pull repo: Repository not found”

The project points at a git remote that no longer exists, or the GitHub App no longer has access to it. Reconnect it, or re-point the project at a repository the app can read.

Dashboards load but every tile is empty

The connector cannot authenticate. Check the project variables the connector reads, then refresh the project. The runtime logs name the missing or rejected credential.

The CLI cannot reach a self-hosted admin

Pass --api-url, and make sure nothing between the CLI and the admin rewrites the response. The CLI expects JSON from the admin's own origin.
